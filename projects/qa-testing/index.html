01Overview

Alongside development, I test software the way people actually use it — following complete workflows, switching between roles, and checking that every step produces the expected result.

When something doesn't behave as expected, I document it so a developer can reproduce it quickly, then retest once it's fixed.

02The Problem

Business software is made of connected workflows. A form that accepts the wrong input, a role that sees the wrong screen, or a status that doesn't update can quietly break everything that follows.

Vague bug reports slow things down further: if a developer can't reproduce an issue, it can't be fixed with confidence.

03Goals

  1. Catch issues before users doValidate features and workflows before and after release.
  2. Make every report actionableClear steps, expected vs. actual result, and priority.
  3. Protect what already worksRetest related workflows after every fix.

04My Role

Because I also develop features, I can test with an understanding of how the software is built — and give developers feedback that's specific and easy to act on.

06Testing Toolkit

Most of my testing is hands-on: structured test cases, browser developer tools to inspect layouts, network requests, and console errors, and checklists for re-running related workflows after a change.

07Challenges

Cross-role coverage

The same workflow behaves differently per role, so each path has to be tested from each role's point of view.

Keeping regressions out

Fixes in one module can affect another; deciding what to retest after each change matters as much as the first test.

08Testing Approach

  1. Understand the requirementWhat should happen, for which role, and under what conditions.
  2. Prepare test casesCover the main flow, edge cases, and invalid input.
  3. Execute and compareRun each case and compare the expected result with the actual result.
  4. Report defectsSummary, preconditions, steps to reproduce, expected vs. actual, and priority.
  5. Retest and regressVerify the fix, then re-check related workflows.

09Improvements

Faster fixes

Reports with reproducible steps let developers go straight to the problem.

Closed feedback loop

Every fix is retested before it's marked done.

Sample QA Report

Fictional defect for a made-up "Demo Booking App".

DEF-102 Priority: High Status: Fixed · Retested
Defect ID
DEF-102
Module name
Appointments → Slot booking
Defect summary
A time slot that is already booked can be booked again by a second user.
Preconditions
Logged in as a front-desk user. Slot 10:30 on the selected date is already booked.
Steps to reproduce
  1. Open Appointments → New booking.
  2. Select "Therapist A" and the date with the existing 10:30 booking.
  3. Select the 10:30 slot.
  4. Fill in the required fields and click "Confirm booking".
Expected result
The 10:30 slot is shown as unavailable and cannot be selected. If submitted anyway, an error appears and no booking is created.
Actual result
The slot can be selected and a second booking is saved for the same time.
Priority
High — causes double bookings.
Status
Fixed → Retested → Closed
Developer comment
"Availability check now runs again on submit. Added a validation message for taken slots."
